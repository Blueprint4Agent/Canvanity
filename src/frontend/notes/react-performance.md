# 상태 소유권과 React 성능

2026-09-27, React 18.3 및 React Compiler 미사용 구성을 기준으로 검토했습니다. 현재 도메인 훅과 범위가 정해진 Provider를 유지하고 Zustand/Redux Toolkit은 아직 추가하지 않습니다. 이 프로젝트의 필요에 따른 판단이며 Context가 항상 빠르다는 의미는 아닙니다.

## 현재 상태와 소유권

| 상태                  | 소유자·변경 빈도                           | 판단                                                                                                       |
| --------------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------- |
| `/config`             | AppConfigProvider; 시작·명시적 갱신·복구   | 요청과 스냅샷을 하나로 공유, Context 유지                                                                  |
| 사용자·세션           | AuthProvider; 로그인·로그아웃·재검증       | 기존 인증 수명주기와 자격 증명 처리 유지                                                                   |
| 데스크톱 연결         | ServerConnectivityProvider; 연결 상태 전환 | 복구 담당자를 하나로 유지하고 별도 저장소로 복제하지 않음                                                  |
| 관리자 목록·API 키    | 도메인 API 훅; 조회·변경·복구              | 서버 상태를 클라이언트 store에 중복 보관하지 않음                                                          |
| 검색 초안·필터·페이지 | 페이지; 입력 시 빈번                       | 로컬 유지, 결과 배열의 참조를 memo 표에 전달                                                               |
| 테마                  | 훅별 상태와 localStorage                   | 동시에 열린 소비자 간 동기화가 필요하면 소유권부터 통합; Provider 또는 범위가 정해진 preference store 검토 |
| 사이드바 너비·펼침    | AppLayout; 드래그·토글                     | 여러 화면이 공유할 때까지 로컬 유지; 포인터 이동마다 저장하는 동작은 별도 최적화 후보                      |
| 최근 계정             | 기존 저장 유틸·이벤트 훅                   | 만료·동의·중복 제거 규칙 유지, 별도 인증/기록 store 추가 금지                                              |

## 라이브러리 도입 판단

| 선택지                                    | 이 프로젝트의 이점                                          | 비용·도입 시점                                                                                                   |
| ----------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 로컬 상태 + 범위별 Context (현재)         | 추가 의존성 없이 기존 수명주기와 테스트 유지                | Context 갱신은 소비자를 렌더링하므로 소유권 분리부터 검토                                                        |
| Zustand (향후 클라이언트 store 우선 후보) | 훅·selector로 자주 바뀌는 공유 UI 상태를 필요한 부분만 구독 | 멀리 떨어진 동시 소비자가 빈번한 상태를 공유하고 측정·소유권 근거가 있을 때 도입; 범위·초기화·selector 먼저 정의 |
| Redux Toolkit                             | 액션·리듀서·도구, 선택적으로 RTK Query                      | 도메인 간 복잡한 상태 전이, 정규화 엔티티, 실행 취소·이벤트 디버깅 또는 의도적인 API 캐시 교체가 필요할 때 검토  |

Zustand는 selector 구독을 지원합니다. 여러 값을 객체로 선택한다면 안정적인 결과 또는 `useShallow`를 사용하고 전체 store 구독을 기본으로 삼지 않습니다. 근거: [Zustand](https://zustand.docs.pmnd.rs/), [useShallow](https://zustand.docs.pmnd.rs/reference/hooks/use-shallow).

Redux도 공유 상태와 변경 복잡도를 기준으로 도입하도록 안내합니다. 선택한다면 Redux Toolkit을 사용합니다. RTK Query는 기존 요청·오류·복구 소유권을 이전하는 별도 설계가 필요하며 캐시를 중복 추가하지 않습니다. 근거: [Redux FAQ](https://redux.js.org/faq/general#when-should-i-use-redux), [Redux Toolkit](https://redux.js.org/introduction/why-rtk-is-redux-today).

향후 store에는 타입이 있는 도메인 액션·selector, 불변 갱신, 계정 변경 시 초기화, 필요한 Provider/요청 격리, 저장 허용 목록이 필요합니다. bootstrap/access token이나 관리자 사용자 목록을 영속화하지 않습니다. HTTP는 도메인 API 래퍼에, 호출 소유권은 페이지의 도메인 훅에 둡니다.

## memo 기반 기본 작업 절차

1. 수정 전에 상호작용, 바뀌는 상태, 렌더링 범위, 상태 소유자를 확인합니다.
2. 입력 초안처럼 자주 바뀌는 상태는 로컬에 두고 기존 API·복구 루프를 유지합니다.
3. 같은 props로 반복 렌더링되는 비용 있는 자식 경계에는 `React.memo`를 기본 적용합니다. 단순 렌더링, 매번 바뀌는 props, Context 자체 갱신 등 적용 효과가 없는 경우 구체적 이유를 남깁니다.
4. 경계를 넘는 배열·객체·함수 참조를 필요할 때 안정화합니다. `useMemo`는 비싼 계산이나 전달 참조에, `useCallback`은 함수 참조가 중요한 곳에 사용합니다. 모든 변수·함수에 일괄 적용하지 않습니다.
5. 불변 데이터, 최신 콜백 값, Context 갱신을 보존합니다. 함수 props를 무시하거나 깊은 비교로 강제로 렌더링을 막지 않습니다.
6. 생략한 작업과 필요한 갱신을 함께 검증합니다. 렌더링·요청 횟수 또는 프로덕션 번들 비교를 기록하고, 체감 지연 개선은 Profiler/브라우저 측정 후 주장합니다.

memo는 얕은 props 비교를 사용하며 자신의 상태나 Context 갱신은 차단하지 않습니다. 성능 최적화이며 정확성의 전제가 아닙니다. 근거: [React memo](https://react.dev/reference/react/memo).

첫 보호 대상은 `AdminUserTable`입니다. 부모는 검색 초안·쿼리·API 상태를 소유하고 원래 items 참조와 loading/error 불리언을 전달합니다. 표는 언어별 날짜 포맷터를 재사용합니다. 날짜가 두 개씩 있는 10행에서 6글자를 입력할 때 추가 날짜 포맷은 0회입니다. 데이터·언어·로딩·오류가 바뀌면 정상 갱신하며 시간 대신 실제 작업 횟수를 테스트합니다. 별도 깊은 비교나 콜백 메모화는 필요하지 않습니다.

## 자동 검사와 한계

- `make react-performance-check`: TypeScript 심볼을 사용한 설정 소유권·보호된 memo 검사, App의 직접 페이지 import 검사, 통과·실패 fixture, 작업 기록 정책 테스트를 실행합니다. 보호된 표에 인라인 객체·배열·함수나 spread props를 전달하면 거절합니다. 변수 뒤에 숨은 재할당까지 증명하지는 않으므로 런타임 검증과 리뷰가 필요합니다.
- `make check` / `make architecture-check`에 포함됩니다. B4FastAPI에서도 `make frontend-architecture-check`를 통해 실행합니다.
- Git 하네스는 런타임 `.ts/.tsx` 및 package/Vite 변경 시 커밋 제목이 일치하는 작업 기록에 **State Ownership**, **Memoization**, **Performance Evidence**를 요구합니다. 테스트 전용·생성 파일은 제외합니다. 미적용 이유는 허용하되 빈 값·placeholder는 거절합니다. 동일한 스테이징/커밋 스냅샷의 템플릿과 기록을 읽으므로 과거 커밋에는 당시 정책을 적용합니다. 근거 기록의 존재를 검사하며 성능 개선 자체를 증명하지는 않습니다.
- `make test`는 관리자 입력 중 불필요한 포맷 생략, 필요한 갱신, 설정 요청 공유·Provider 격리·복구 순서를 검증합니다. `make test-routes`는 빌드 후 실제 청크의 지연·실패·복구를 확인하고 로컬 전체 검증에서도 Chromium으로 실행합니다.
- `make test-ui`는 레이아웃·인증·역할 흐름을 검증합니다. UI 변경 시 실행하며 이전 작업의 테스트 생략을 이후 작업에 적용하지 않습니다.
- 보조 화면의 lazy 로딩을 유지합니다. 분할 직후 진입 JS는 426.68 kB(gzip 130.36)에서 390.76 kB(gzip 121.26)로 감소했습니다. 공유 CSS는 그대로이며 이 값은 측정 기록이지 보편적 예산·응답 시간 보장은 아닙니다.

독립적으로 검토할 수 있는 최적화는 별도 브랜치·작업 기록·PR로 진행합니다. store 도입, 보호된 경계 변경, React 업그레이드 또는 Compiler 도입 시 기준을 재검토합니다. memo 개수 자체를 목표로 삼지 않습니다.

인증된 API 요청은 공통 전송 계층의 갱신 작업 하나를 공유하며 INVALID_TOKEN 발생 시 한 번만 재시도합니다. AuthProvider가 갱신을 담당하고, 재귀 호출 방지를 위해 /auth/me GET 및 로그아웃은 기존 인증 흐름이 처리합니다. 늦은 401은 갱신된 토큰을 재사용하며 로그인·로그아웃 시 이전 요청의 재시도를 차단합니다. 요청 본문과 멱등성 ID는 유지합니다. 구독은 창 포커스 및 정상 토큰 갱신으로 다시 조회하지 않습니다. 최초 진입·명시적 새로고침·결제 복귀 시 조회하며 같은 인증 정보의 동시 조회만 공유하고 구독 상태를 영구 캐시하지 않습니다.

SubscriptionSnapshotProvider가 계정별 구독 상태를 공유합니다. 화면 이동은 저장값을 재사용하고 변경 응답은 바로 반영하며 명시적 새로고침·결제 복귀 때 서버 DB를 조회합니다. 포커스·온라인 이벤트·타이머 반복 조회는 없습니다. 계정 전환 시 상태를 초기화하고 데스크톱 복구 시 같은 계정 상태를 유지합니다. API 계층의 진행 중 요청 공유는 단독 소비자를 보완합니다.
